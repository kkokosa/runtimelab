Generated 2026-08-03 11:26:16 on this machine. 11 workloads, each run once per GC configuration (Workstation, Server, LXRGC), on the custom pluggable-write-barrier runtime.

Workstation GC (default, non-concurrent-by-default background GC) Server GC (DOTNET_gcServer=1, per-core heaps) LXRGC (LXR: coalescing reference counting + backup trace + Immix sweep, stop-the-world)
What is LXRGC? LXRGC is a custom standalone CoreCLR GC (loaded via DOTNET_GCName=LXRGC.dll) that implements the LXR collector (“Low-Latency, High-Throughput Garbage Collection”, Zhao, Blackburn & McKinley, PLDI 2022 — arXiv:2210.17175) as a sibling to the author's earlier UpsilonGC experiment. It implements the full IGCHeap/IGCHandleManager ABI over a real Immix substrate (32 KiB blocks / 256 B lines, per-thread bump allocator), and performs algorithmically-full stop-the-world reclamation: coalescing reference counting driven by the runtime fork's generic pluggable write barrier (which surfaces the overwritten field value), recursive zero-count freeing, a periodic backup trace (under SuspendEE, marking from handles + GcScanRoots) that collects the dead cycles pure RC cannot, and an Immix sweep that MEM_DECOMMITs fully-dead chunks and recycles them. Collection is triggered by an allocation-growth budget. It exposes the same GC.CollectionCount, GC.GetTotalAllocatedBytes, and GC.GetGCMemoryInfo() counters as the built-in GC. This report compares it against both default GC modes (Workstation and Server) across every workload, using dotnet-counters to capture real second-by-second time series (not just end-of-run summaries) for GC pause time, memory, and throughput.

How to read this: LXRGC does collect — it reports real collection counts (with equal gen0/1/2 numbers, since each cycle is a unified full-heap stop-the-world pass) and non-zero GC pause time while a backup trace + sweep runs. As a young research collector it is throughput-competitive with the built-in GC across these workloads, but over-commits memory: its working-set/committed-bytes footprint is typically much higher than Workstation/Server GC because its Immix sweep reclaims coarsely (at chunk granularity, no evacuation/compaction yet) and its allocator over-reserves. The gap in the memory rows is the honest cost of a from-scratch GC versus the mature, compacting built-in collector; the throughput rows show that RC + periodic tracing keeps pace on these patterns.
A note on the Total allocated row: GC.GetTotalAllocatedBytes(precise: false) — the counter all three modes report through — is documented as a fast approximation on the built-in GC: each thread allocates from a private bump-pointer “allocation context” and the imprecise counter only reconciles those contexts opportunistically, so with many concurrently-allocating threads it can noticeably undercount true allocation volume between reconciliations. Small differences in this row across GC modes therefore partly reflect counter-precision, not solely a difference in actual allocation behavior; the working-set/committed-bytes/heap-size rows (which come from OS/GC-heap accounting, not this approximate counter) are the more apples-to-apples memory comparison.
